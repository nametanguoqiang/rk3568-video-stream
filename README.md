# RK3568 视频采集与推流终端

在 RK3568 开发板上打通从摄像头采集到网络推流的完整链路。

> 项目进行中，当前完成到第 5 步（连续采集与帧率统计）。推流、抓拍等模块在后续步骤实现，进度见下表，没做的部分不写成已完成。

## 为什么做这个项目

之前做的项目都在应用层，界面、协议、文件传输，数据是别人准备好的。这个项目要从摄像头一路打通到网络，中间每一层都自己管：V4L2 的缓冲、多线程的同步、网络的异常、长时间运行的资源占用。

目标不是把画面显示出来，是把一条实时数据链路做稳，并且能说清每一处为什么这么设计。

## 运行

```bash
# 传到板子
scp probe root@<板子IP>:/root/

# 运行，参数是设备节点
ssh root@<板子IP> "chmod +x /root/probe && /root/probe /dev/video0"
```

输出包含驱动名、设备名、采集类型（单平面或多平面）、支持的像素格式和分辨率范围。

## 关键设计

**为什么用 mmap 四缓冲**：read 方式要内核拷到用户态，一次拷贝。mmap 把内核缓冲直接映射进进程，零拷贝。四块是周转和内存的平衡点，两块容易卡，太多浪费。

**为什么用环形缓冲**：视频是定长的、连续的，旧的没用了就扔。环形缓冲一次分配用到底，不会碎片，也不会因为 malloc 阻塞采集线程。

**为什么丢最旧的一帧**：视频要实时，丢新的会让延迟越攒越大。

**为什么先做 HTTP MJPEG 不做 RTSP**：MJPEG 不需要编码器，摄像头直接出 JPEG，两天能通。RTSP 要 RTP 打包和 SDP 协商，工作量五倍。

## 实测指标

在 RK3568 上跑 300 帧连续采集，数据来自程序自己统计的时间戳。

| 分辨率 | 帧大小 | 平均帧率 | 平均间隔 | 最大间隔 | 最小间隔 |
|---|---|---|---|---|---|
| 1280x720 MJPG | 约 41 KB | 15.1 fps | 66.4 ms | 68.4 ms | 63.9 ms |
| 640x480 MJPG | 约 18 KB | 15.1 fps | 66.4 ms | 68.4 ms | 63.9 ms |

### 为什么只有 15fps

这颗摄像头（Logitech C270，046d:0825）实际输出固定 15fps，**不是代码问题，也不是带宽问题**。排查过程：

| # | 查什么 | 结果 |
|---|---|---|
| 1 | 硬件声明支持哪些帧率（`VIDIOC_ENUM_FRAMEINTERVALS`） | 720p 和 640x480 都列了 30fps |
| 2 | `VIDIOC_S_PARM` 设 30fps | 成功 |
| 3 | `VIDIOC_G_PARM` 设完读回 | `1/30`，驱动确实记下了 |
| 4 | `VIDIOC_G_PARM` 开流后读回 | `1/30`，UVC 协商没有偷改 |
| 5 | USB 协商速度 | 480 Mbps（USB 2.0 高速），带宽充足 |
| 6 | `dmesg` 看驱动日志 | 无带宽或传输错误 |
| 7 | 降到 640x480 重测 | **帧率完全不变，仍 15.1fps** |

第 7 条是关键：分辨率降到四分之一、帧大小降到一半，速度纹丝不动，说明瓶颈不在 USB 链路，而在摄像头固件。66.4ms 的间隔非常规整（最大最小只差 4.5ms），是摄像头内部定时器的固定节拍。

**驱动认为自己在跑 30fps，硬件按 15fps 出数据。** 这是 UVC 1.00 老协议设备的已知行为，用户态改不了。
